## Summary

Pancreator is a Cursor-native workflow harness written in strict TypeScript and Bash. Cursor supplies model execution and MCP access; the dependency-free Node.js CLI owns workflow snapshots, state transitions, deterministic gates, retries, validation evidence, and audit records. This checkout is the self-development source (`config.json.installation_mode: self_development`, version `7.23.0`). `library/` is canonical for workflows, personas, skills, Cursor projections, schemas, and templates; `governance/` holds policies, registries, criteria, and durable handbooks; `runtime/` holds generated run state and evidence, and `worktrees/` holds operator, cohort, and best-of-N checkouts. `/pan-start` and `/pan-resume` adopt the supervisor brief in the operator's session and advance one run at a time; `/pan-cohort` supervises a fan-out of chunk runs and `/pan-horizon` supervises a queue of tasks across a long absence. The supervisor delegates each worker stage to a named persona subagent, or to an external executor when the persona mapping carries the `claude-code:` or `openai:` prefix; `pan delegate --headless` dispatches a Cursor-executor stage through the harness's own `cursor-agent` path when the platform exposes no projected agent. `planning` is the default workflow and the entry point for delivery work: it runs one `plan` stage behind one operator gate, and approving that gate routes the work automatically into either one `delivery` run or a cohort of parallel `delivery-chunk` runs followed by one release run. Each run snapshots its own workflow graph, persona-model mapping, operator-involvement profile, review mode, and verification level at creation, so later configuration edits never change a run in flight. A run also renders a supervisor governance card that the supervisor must attest, and the supervisor must observe every delegated worker through `pan watch` before the harness accepts a submission. Deterministic verification is tiered: one shared `static` and `fast` baseline is captured per unit of work, agents iterate on the `impacted` profile, and the `full` profile runs only as the ship stage's release gate. The harness also keeps that work off the supervisor's critical path: a run adopts a recorded passing baseline taken at the same workspace fingerprint and verification-configuration digest, an agent's own clean profile pass is stored where the submit gate already looks, a source stage that submits into a read-only evidence stage starts a detached low-priority prefetch of the ship release profile, and a worker model probe records a `pending` marker and answers from a detached child instead of blocking the launch. Every policy instruction carries an audience, so a worker card, a supervisor card, and the harness-only audit snapshot each receive only the instructions written for them, and a delegated supervisor procedure points at per-policy section digests instead of repeating policy bodies. Optional `pan hypervisor`, `pan away`, `pan horizon`, and `pan schedule` subsystems add agent-health recovery, bounded unattended continuation, long-horizon task queues, and calendar triggers; away mode and the scheduler are disabled in `config.json`. Standalone command-backed modes cover authoring target extensions (`pan author`), auditing the harness test suite (`pan tune`), removing unused harness facilities (`pan debloat`), local release preparation (`pan release`), Simplified Technical English repair of operator-timed prose (`pan conform`), judgment-level code style repair (`pan style`), report-first retention cleanup of harness runtime state (`pan cleanup`), and Cursor token spend reporting (`pan spend`). `bin/install` packages the harness into another repository in embedded or detached mode while leaving that target the owner of application source, tracked files, existing agentic tooling, and Git state. The harness test suite is self-development-only and is not part of an installed payload. Repository validation is installation-scoped for the same reason: the audits that describe Pancreator's own source authoring run only when `config.json.installation_mode` is `self_development`, so a fresh embedded install reports zero validation errors and zero warnings.

## Administrative commands

### Install

- Node.js 22 or newer, npm, and Git are required; `package.json` declares `engines.node >= 22.0.0`. Cursor needs project commands and subagents enabled. The Claude Code CLI is needed only for a `claude-code:` persona mapping, `OPENAI_API_KEY` only for an `openai:` one, and an `admin:*`-scoped `CURSOR_ADMIN_API_KEY` only for `pan spend`.
- `npm ci` installs the locked development toolchain (TypeScript, Node types, Prettier). There are no runtime dependencies. It is also the workspace bootstrap recorded in the `setup` array of `runtime/repository-checks.json`, because a fresh worktree carries no installed dependencies.
- `npm run prepare` points `core.hooksPath` at `.githooks/`, which holds `pre-commit` and `pre-merge-commit`. Both call `bin/check-landing`, which refuses a direct installable commit on `pan-dev` or `main` and a merge whose source branch carries no new indexed release. `bin/check-landing branch <ref>` reports landability without committing.
- `./bin/pan models --sync` renders canonical Cursor assets and the active model mapping into the ignored local `.cursor/` tree. Run it after cloning and after any `active_config` or mapped-model change. `--force` with `--sync` projects the configured specs when the local Cursor model catalog is stale or incomplete.
- `./bin/install --target /path/to/target-repository` builds an embedded harness at `<target>/.pancreator`; add `--harness-dir /outside/path` for a detached installation, which must sit outside the target tree.
- `--yes`, `--repair`, `--clean`, and `--smoke` provide idempotent refresh, in-place repair, full reinstall, and the deterministic installer smoke harness. Installation writes the target's clone-local `.git/info/exclude` and never modifies a target-tracked file or the target `.gitignore`.
- The installed payload excludes `tests/` and `dist/tests/`, and `bin/install-support strip-harness-test-scripts` removes every `test` and `test:*` script from the staged `package.json`. `tests` is a retired payload entry: a refresh from an older installation deletes only the files whose recorded release digest still matches, backs up and retains anything changed or target-added, and reports both sets.
- Installation also appends a guarded `pan` shell function to the operator's Bash and Zsh rc files. `--skip-shell-alias` suppresses that step, and the installer smoke harness always passes it.
- `./bin/update --target /path/to/target-repository [--harness-dir /outside/path] [--skip-shell-alias]` fast-forwards an installation from an indexed release.

### Build

- `npm run build` calls `./bin/run-built --build-only`, which serializes builds on a per-root lock and delegates to `bin/build`. `bin/build` compares a fingerprint stamp of `tsconfig.json`, `package.json`, `package-lock.json`, and every `src/` and `tests/` TypeScript file against `dist/.build-stamp`, and rebuilds by removing `dist/` and running `tsc` only when the stamp is stale.
- A stale stamp compiles into a private `dist.build-<pid>` staging directory and swaps it into place with two renames, so `dist/` is never absent or half-written and a build never waits for a running consumer. A long-lived `pan watch` therefore cannot delay a build on its root.
- `./bin/build --stamp-fresh` reports whether `dist/` already matches its inputs, and `npm run typecheck` runs `tsc --noEmit`.
- Every `./bin/pan ...` invocation goes through `bin/run-built`, which builds when needed under a per-root lock held only for the compile, and then dispatches `dist/src/cli.js`. A caller that waits more than `PANCREATOR_BUILD_LOCK_NOTICE_SECONDS` (default 5) for that lock prints one notice naming the holder pid. `bin/openai` dispatches `dist/src/openai-cli.js` the same way.

### Test

- `npm test` is the documented default suite: it builds, then runs `node --test` over the compiled `unit`, `integration`, and `regression` lanes only, at `--test-concurrency=${PAN_TEST_WORKERS:-13}`. Every test script routes through `bin/run-tests` and the compiled `tests/reporters/failures-only.ts` reporter, so a passing run prints almost nothing. The lanes currently hold 92 unit, 146 integration, 25 regression, and 9 secondary test files.
- `npm run test:unit`, `npm run test:integration`, and `npm run test:regression` run the individual compiled subsets. `npm run test:secondary` runs the `tests/secondary/` lane, which owns the installer suites and is outside `npm test`.
- `./bin/pan tests impacted [--worktree <name>] [--changed <ref> | --staged | --worktree-dirty] [--file <path>]... [--include <glob>]... [--depth <n>] [--list] [--json] [--advisory-ratio <0..1>]` (equivalently `npm run test:impacted`) is self-development only. It builds the runtime import graph of `src/` and `tests/`, selects the mainline lane tests the changed files reach, and runs them with the failures-only reporter. It is the iteration profile (`impacted` in `runtime/repository-checks.json`) and never a gate; it appends each run to `runtime/cache/test-impact.jsonl` and advises using `fast` instead once the selection reaches 60% of the lane. Under `DEV-001`, `REMED-001`, and `VERIFY-001` it is the only profile an implementing or evidence agent runs while iterating.
- `./bin/pan tests wall` reports the rolling 24-hour fast-lane wall average against the `fast_wall` ceiling in `config.json` (120000 ms, with `max_load_average_per_cpu` and `minimum_qualified_samples` filters). `./bin/pan tests benchmark --baseline-workspace <path> --candidate-workspace <path> --population-tolerance <count>` captures both sides of a paired comparison in one session record, and `npm run benchmark` (`bin/benchmark`) times the `fast` or `full` profile three times in one workspace.
- `npm run test:coverage` runs every compiled lane, including `secondary`, and enforces 80% line and function coverage and 70% branch coverage over `dist/src/lib/**`. Because it covers every lane once, the `full` profile pairs it with `npm run check` rather than re-running `npm test`.
- `./bin/install --smoke` runs the deterministic embedded-installer smoke harness. It also asserts that a fresh install carries no `tests/`, no `dist/tests/`, and no test scripts, and that a refresh removes an unmodified retired `tests/` payload.
- `tests/secondary/embedded-installation.test.ts` is the self-development leakage guard. It installs an embedded harness, runs `pan doctor` inside it, and asserts `validation.ok` with empty `errors` and `warnings`. A new check that only makes sense for Pancreator's own source must therefore be installation-scoped, or that suite fails. Run it through `npm run test:secondary`, not `npm test`.
- `bin/run-tests` owns one scratch directory per suite run under `runtime/tmp/tests.noindex/`, exports it as `PANCREATOR_TEST_TMP`, and discards it at exit by renaming it to `discarded-<id>` and starting a detached `rm -rf`, so the command ends when its assertions end. The next run sweeps any run directory whose owner process is gone and any discarded tree whose remover is gone.
- Fixture construction is shared rather than repeated. `tests/shared-template.ts` builds one fixture template per suite run under that scratch directory, behind a lock and published by rename, and every other test process clones it; `tests/fixture-template.ts` holds the template and its clones and deliberately imports no engine module, so a fixture-only test is not dragged into the impacted selection. A test file run outside `bin/run-tests` falls back to its own per-process build.
- `TEST-001` and `governance/handbooks/eng/testing.md` define when a self-development test earns its place in the suite. `./bin/pan tune prepare|finalize|validate-audit` runs the standalone audit of that suite and writes ranked records under `runtime/tune-harness/` without editing any test.
- `npm run test:migrations` is still declared, but no `tests/migrations/` directory exists, so the script matches nothing.
- `PAN_TEST_PROFILE=<path>` makes the reporter write per-test and per-file durations to that JSON path. The harness sets it for exactly one `full`-profile gate before ship, and the result is advisory rather than a gate. The variable name lives alone in `src/lib/suite-profile-env.ts` so the reporters do not import the run layout.
- `bin/run-tests` also exports `PAN_PREFETCH_FULL=0` unless the caller already set it, because several suites assert exactly how many times a profile executed and the release-profile prefetch would make those counts depend on scheduling.

### Other

- `npm run format` and `npm run format:check` apply or verify Prettier formatting over explicit top-level paths (`bin docs evals governance library release src target-extensions tests` plus root `*.json`, `*.js`, and `*.md`) with Prettier's content cache enabled. `tests/regression/format-script-coverage.test.ts` fails when that path list stops reaching a tracked file Prettier supports.
- `npm run lint` runs `format:check`, then `bash -n` over every Bash script in `bin/`. It runs `typecheck` only when `bin/build --stamp-fresh` reports a stale build stamp; a fresh stamp proves the emitting build already type-checked the same program.
- `npm run check` runs `build`, `lint`, and `validate` in that order through `bin/check`, so the fresh build stamp lets `lint` skip its own `typecheck`. Test execution belongs to the profile commands (`npm run test:coverage`, `./bin/install --smoke`), so a passing check never runs the suite.

It also runs three registry-integrity checks that fail when a policy reaches no card: policy-to-lookup-row coverage, per-row instruction delivery at that row's card audience, and audience-to-card-producer delivery, plus a handbook-coverage check that follows a standalone mode when a handbook belongs to one instead of to workflow personas. Parts of the sweep are self-development-only, behind `isSelfDevelopmentInstallation`: the directive-ownership audit, the test scratch-directory audit, the harness-instruction coverage check, the supervisor-delegation guidance check, the primer-drift warning, and three extra required files (`docs/operator-briefs/project.json`, `docs/operator-briefs/project.css`, `library/skills/review-squad-pancreator.md`).
- `npm run validate:chat-markdown` validates fenced Markdown intended for Cursor chat, from stdin or a file path.
- `./bin/pan doctor [--worktree <name>] [--json]` reports Node support, workspace and worktree resolution, Git availability and the integration branch, browser-automation readiness, Cursor authentication and its `.env` source, the active pipeline mapping, the Cursor model catalog, gate-cache state, primer freshness, repository-check probe coverage, and repository validation.
- Deterministic shell gates accept a recorded clean pass of the identical command at an unchanged Git workspace fingerprint for 24 hours (`DEV-001`); the cache lives at `runtime/cache/gate-results.json`, a result so accepted is marked `cached`, and `PAN_GATE_CACHE=0` forces every gate to execute. The cache is harness-owned, so agents must not set or clear that variable. Three behaviors feed it: baseline capture adopts an earlier passing baseline artifact taken at the same profile, workspace fingerprint, and repository-check configuration digest; `pan repository-check <profile> --run <run-id>` records its own clean pass when no command timed out and the Git fingerprint is identical before and after; and a source stage that submits into a read-only evidence stage starts one detached low-priority run of the ship entry gate's profile, recording the child pid under the run's evidence directory. `PAN_PREFETCH_FULL=0` stops that prefetch, and a killed or failed prefetch simply leaves nothing behind.
- `./bin/pan init --request runtime/inbox/queue/<file>.md [--workflow planning|delivery|prototype|design] [--title <title>] [--workspace <dir> | --worktree <name>] [--gates <file>] [--involvement <profile>] [--verification <level>] [--with-design] [--operator-artifacts] [--context-reference <file>] [--no-autostart | --autostart [--max-parallel <n>]]` starts a run; the default workflow is `planning`, and `--with-design` composes design planning into it. `prepare`, `delegate`, `watch`, `worker record|state`, `submit`, `assess`, `decide`, `pause`, `attribute`, `resume`, `set-stage`, `waive-gate`, `abort`, and `archive` cover the rest of the lifecycle.
- `./bin/pan cohort init|start|status|integrate|release|abandon|clean|route` drives the plan fan-out. `start` creates one worktree and one `delivery-chunk` run per unstarted chunk of the next cohort up to the parallelism limit, `integrate` retries the one merge that failed to advance automatically, `release` is the merge-free retry of the release continuation, and `route` is the idempotent retry of a failed plan route.
- `./bin/pan watch <run-id> [--invocation <id>] [--cadence-seconds <n>] [--stall-timeout-seconds <n>] [--timeout-seconds <n>] [--mark-background] [--launched-at <iso>] [--handle <id>] [--agent-state running|completed]` is the harness-owned worker timer. It records every arming and wake to `agent/evidence/<invocation-id>-watch.jsonl` and exits `0` on a present output, `2` on a stall, `3` at the timeout, and `4` when the completion is unverified. `--agent-state` reports what the supervisor saw when it inspected the launched agent, because the watch reads files and cannot see a worker that is still writing. `./bin/pan watch --targets <run-id>:<invocation-id>[,...]` is the multiplexed cohort wait that returns on the first target that changes, and `./bin/pan watch <run-id> --foreground-returned [--launched-at <iso>]` records a returned foreground launch instead.
- `./bin/pan worker record <run-id> --handle <platform-handle> [--invocation <id>] [--role <evidence-role>] [--new-attempt]` records the platform identity of a launched worker, and `./bin/pan worker state <run-id>` reports the last known state of every recorded worker and each declared path on disk.
- `./bin/pan attribute <run-id> --note <directive> [--role supervisor|operator] [--disposition read-only-input|commit-with-unit|operator-owned] [--paths <p,...>]` records an operator directive executed against the workspace outside a stage, so the next invocation card lists those paths as already attributed.
- `./bin/pan status <run-id> --redline --occasion <pan-start|pan-resume>` writes the platform-guidance redline record the supervisor owes at every start and resume; `--resolve <citation>` maps a stale artifact citation through the run's invocation alias map.
- `./bin/pan inbox [--json]` lists the request files under `runtime/inbox/`, which is partitioned by lifecycle status, and `./bin/pan inbox restore <inbox-file>` returns a canceled or active item to `queue/`. `./bin/pan archive [--days <n>] [--complete] [--canceled] [--json]` applies the archive tier of runtime retention, reading its window from `config.json.retention` (default 30 days) unless `--days` overrides it for one command.
- `./bin/pan cleanup [--days <positive-integer>] [--class <name>]... [--apply] [--json]` is the deletion tier. It reports the complete plan by default and mutates only with `--apply`. `CLEANUP_ARTIFACT_CLASSES` in `src/lib/cleanup.ts` names every class it touches: workflow and standalone runs, best-of-N and cohort sessions, traces, evals, horizon, hypervisor, away mode, orchestrator events, terminal inbox history, PR descriptions, research, benchmarks, scratch, and managed worktrees, plus the durable `retain` classes for the conform and style checkpoints, `runtime/release/allocations.jsonl`, and `runtime/repository-checks.json`. The apply also reconciles inbox lifecycle directories, relocates legacy loose inbox files, renames surviving loose files onto the temporal convention, and retires aged clean worktrees while keeping every branch.
- `./bin/pan spend [--days <1..365>] [--json]` fetches team usage events from the Cursor Admin API (`POST https://api.cursor.com/teams/filtered-usage-events`, Basic authentication, 1000-event pages, 60-second per-request timeout) and returns one aggregate report. The default window is 14 days. It resolves `CURSOR_ADMIN_API_KEY` from the process environment or an installation or workspace `.env`, and never emits raw events, credentials, email addresses, conversation ids, or cloud agent ids. `./bin/pan context digest <file>` prints the trimmed-content digest an audited context reference states, and `./bin/pan context card <run-id>` renders one invocation card read-only from its recorded snapshot.
- `./bin/pan hypervisor start|run|tick|status|stop [--json]` runs the agent-health loop that reconciles the agent registry and drives bounded recovery. `./bin/pan away status|evaluate|apply <run-id> [--decision <id>] [--action <action>]` drives bounded unattended continuation under `AWAY-001`.
- `./bin/pan release allocate --worktree <name> --bump <major|minor|patch> [--run <run-id>]` hands out the next release version above every published and allocated one and records it in `runtime/release/allocations.jsonl` before any release commit exists, so two concurrent release runs cannot select the same version. `./bin/pan release sync|continue|finalize --worktree <name>` then performs local release preparation: checkpoint, rebase onto a fetched main, and finalized release commits. Finalization refuses a version it holds no allocation for, and refuses one that already exists on the tip of `pan-dev` or the local default branch. In self-development it also refuses an unclean conform pass with `RELEASE_CONFORM_UNCLEAN` and an unclean style pass with `RELEASE_STYLE_UNCLEAN`, each naming its repairing command; `--allow-unclean <conform|style>` is repeatable and lands in `overridden_quality_passes` on the result. Publication stays an operator action.

- `./bin/pan schedule list|status|tick|validate|install-agent|uninstall-agent` and `./bin/pan schedule run <job-id>` evaluate configured calendar jobs and manage the opt-in macOS launchd trigger; any platform can invoke `pan schedule tick` from an external trigger. `config.json.schedule.enabled` is `false` in this checkout.
- `./bin/pan installs list` and `./bin/pan installs archive <install-id> --intake <path> --item <path>` report registered installations, flag a stale one against its `harness_version`, and archive only the installation inbox items a validated consolidated intake cites.

- `./bin/pan debloat scan|adjudicate|select|impact|verify` is self-development only. `scan` inventories the functional dependency graph, runs an independent orphan check, reads every evidence file in the usage window, and writes an operator report under `runtime/debloat/` without removing anything; `adjudicate` records an agentic verdict for one unclear candidate; `select` accumulates the operator's chosen ids; `impact` computes the exclusive-reference closure with the freed paths and symbols; and `verify` fails while a listed path, freed entry, or reference to a removed facility survives.
- `./bin/pan eval list|run|grade` executes the on-demand harness evals over the JSON scenarios in `evals/scenarios/`; see `docs/evals.md`.
- `./bin/pan pr-description context [--worktree <name>] [--json]` collects the branch facts a pull-request description needs.
- `./bin/pan involvement`, `./bin/pan verification [<run-id>]`, and `./bin/pan verification <run-id> set <level> [--confirm]` inspect gate profiles and verification levels, and change the level of a run already in flight.
- `./bin/pan repository-check <profile> [--timeout-ms <ms>] [--workspace <dir|worktree> | --worktree <name>] [--run <run-id>] [--role <evidence-role>] [--force-repeat]` runs a configured verification profile; `./bin/pan repository-check validate --json` validates the profile file without executing its commands. The resolved bound is one budget for the whole profile: probes and commands share a single deadline, and the first entry that exhausts it stops the rest. A `--run` request that matches a recorded pass for the same invocation, role, profile, and fingerprint returns that pass instead of executing, and `--force-repeat` executes anyway. `--harness-initiated` marks the execution as harness-started and suppresses streaming; the harness authorizes it with a launch token it hands the child it spawns, so a caller that passes the flag without that token is refused with `HARNESS_INITIATION_UNVERIFIED`.
- `./bin/pan conform scan|checkpoint [--since <ref> | --all] [--worktree <name>] [--json]` selects the operator artifacts and harness instruction surfaces that `STE-001` covers and reports their Simplified Technical English issues. The harness-owned `docs/issues/**/*.md`, `runtime/pr-descriptions/*.md`, and `runtime/research/*.md` are editable, and so are the instruction surfaces `AGENTS.md`, `governance/criteria/*.md`, `governance/policies/*.json`, `library/personas/*.md`, `library/skills/*.md`, `library/cursor/commands/*.md`, and `library/cursor/rules/*.mdc`. A policy file is read through its `instructions[]` entries, including the `text` of an audience-tagged entry, under the `policy-json` target type of `SIMPLIFIED-ENGLISH-VALIDATE-001`. `governance/handbooks/` stays out, because a handbook is guidance rather than instruction text. Rendered `runtime/logs/workflows/**/operator/*.html` is report-only, and so is `CHANGELOG.md`, which a ship stage and `/pan-release` own and which is scanned only in self-development. No target-tracked path is editable. `scan` honors the selection flags and compares each file against `runtime/cache/conform.json`; `checkpoint` always inspects the complete eligible set, returns `blocked` without writing while any editable file still has issues, and writes that checkpoint once the set is clean. Both subcommands exit `1` on a non-passing status. In self-development the tracked instruction surfaces and `docs/issues/` resolve against the selected workspace, so `--worktree` moves them, while the installation root keeps the runtime artifacts. In a target installation those same instruction surfaces resolve against the harness root instead.
- `./bin/pan style scan|checkpoint [--since <ref> | --all] [--worktree <name>] [--json]` is the second batch pass. It reports the countable code style issues of workspace source whose extension a detected language owns (`.ts`, `.tsx` for TypeScript, `.py`, `.pyi` for Python, and the JavaScript extensions), counted by `CODE-STYLE-VALIDATE-001`, and writes `runtime/cache/style.json` on a clean checkpoint. Unlike conform it is a workspace mode: in an embedded installation the target repository is the workspace and the harness at `<target>/.pancreator` is report-only. `npm run lint`, or the formatter the target declares, stays authoritative for mechanical style, so the pass repairs only judgment-level rules.
- `./bin/pan technologies detect [--worktree <name>] --json` reports detected target languages and unsupported evidence from Git-tracked paths.
- `./bin/pan worktree create|resolve|list|remove|reconcile` manages operator worktrees under `worktrees/operator/`.
- `./bin/pan best-of-n init|status|refresh-agents|abandon|consolidate|clean|prune` manages a best-of-N session.
- `./bin/pan governance card --mode <author|best-of-n|build-briefs|build-docs|cleanup|conform|debloat|decomposition|harden|pair|polish|qa-workflow|release|repair|research|review|shepherd|spend|spotfix|style|supervisor|target|trace|tune-harness|unbound|write-pr>` generates the governance card every non-workflow mode requires; `--mode supervisor --run <run-id>` refreshes a run's supervisor card. `--mode review` also accepts `--base <ref>` and `--dimensions <a,b,c>`. `./bin/pan governance attest-supervisor <run-id> --sha256 <digest>` records the supervisor's attestation, `./bin/pan governance review-scope --target <ref>` reports a review target's conflicts of interest by tier, and `./bin/pan governance audit-directives` reports normative directives that no policy owns.
- `./bin/pan models [--sync] [--force] [--probe] [--migrate-from <previous-config.json>] [--json]` resolves and projects the active mapping; `--force` with `--sync` projects configured specs when the local catalog is stale or incomplete; a bare `--probe` launches one minimal `cursor-agent` call per distinct model spec and needs that CLI plus credentials. `./bin/pan models --probe --run <run-id> --invocation <id> [--await-probe]` probes one worker invocation: without `--await-probe` it records a `pending` marker, starts a detached child, and returns, and the child carries `--await-probe` to perform the live call. `./bin/pan models evidence --run <run-id> --role supervisor --effective-model <model> --source <source>` records the supervisor's own effective model.
- `./bin/pan briefs build|validate|render|generate`, `./bin/pan validation-map`, `./bin/pan requirements resolve|run`, `./bin/pan output scaffold|validate`, `./bin/pan assessment scaffold`, and `./bin/pan spotfix scaffold-escalation` cover briefs, validation auditing, and artifact scaffolding.

## Architecture

```mermaid
flowchart LR
  Operator[Operator in Cursor] --> Commands[Projected `/pan-*` commands]
  Commands --> Supervisor[Supervisor in operator session]
  Supervisor --> Pan[`./bin/pan`]
```

## Gotchas

- `.cursor/` is disposable local projection, not source of truth. Canonical content lives under `library/cursor/`, and drift is resolved with `./bin/pan models --sync`.
- The tracked `config.json` ships every `defaults` persona as an empty string, and an empty `defaults` entry is rejected at load. This checkout therefore depends on an untracked `config_overrides.json` that supplies the effective persona models; `./bin/pan doctor` reports the resolved mapping it actually loaded. The installer merges the source checkout's overrides so an install ships effective specs even though the tracked file is blank. That overrides file can also still map retired personas such as `investigator` and `repo-technician`, which `pan doctor` echoes even though no persona file exists for them.
- Cursor model availability is account-specific, so `governance/registries/cursor_model_catalog.json` stays on the operator's disk and out of shared history. `.gitignore` ignores it and `bin/install` deletes it from the staging payload, so it never reaches a target installation. The catalog is optional: with it present, an unknown model, parameter, value, or variant combination fails config loading loudly; without it, persona specs are checked for grammar only. Repository validation does not list it as a required file.
- `./bin/pan` builds before dispatch, but `bin/build` skips `tsc` when `dist/.build-stamp` still matches the TypeScript inputs, so a rebuild is not proof that compilation just ran. Verification scripts are silent on success through `bin/run-quiet`; set `PAN_VERBOSE=1` to stream output while diagnosing a failure.
- Nothing lands on `pan-dev` without a release. `.githooks/pre-commit` and `.githooks/pre-merge-commit` call `bin/check-landing`, which refuses a direct installable commit on `pan-dev` or `main` and a merge whose source branch carries no new indexed release. `npm run prepare` wires `core.hooksPath`, so a clone that never ran an npm lifecycle script has no guard.
- A supervisor session is gated twice. `pan prepare` and `pan submit` fail with `SUPERVISOR_CARD_UNATTESTED` until `pan governance attest-supervisor` records the current `agent/supervisor-card.md` digest, and with `REDLINE_MISSING` until `pan status <run-id> --redline` writes a declaration for the current session generation. Every attestation opens a new generation, so a resume needs a fresh redline even when the digest did not change.
- `pan submit` refuses a Cursor worker output with `DELEGATION_UNOBSERVED` unless a completed `pan watch` record or a `--foreground-returned` attestation proves the worker reached a terminal state. A watch that ends `unverified` (exit `4`) does not satisfy that requirement: one confirming wake could not settle the observation, because the output was younger than one cadence, the elapsed time was unreadable, or the agent was reported as running. Stages that `pan delegate` runs through an external executor are exempt only when the delegation-execution record names the run and invocation.
- Every argument the CLI passes through argv is refused at or above 900 bytes with `ARGV_ELEMENT_TOO_LARGE`, because endpoint security kills a process whose argv element reaches 1000 bytes before Node starts. Use `--note-file` instead of `--note` for a full decision packet; `decide`, `pause`, `resume`, `set-stage`, and `waive-gate` all accept it.

The `./bin/pan governance audit-directives` command and the `directiveAuditHandler` requirement validator stay ungated and still report in any installation. `governance/registries/directive_exemptions.json` records intentional exclusions.
- `docs/embedded-installation.md` still documents target context-bloat dispositions under `governance/registries/context_bloat_dispositions.d/<extension-id>.json`. That target-owned mechanism still exists and `pan governance audit-directives` still evaluates it, but a target's `pan validate` sweep no longer does. Treat `src/lib/validation.ts` as authoritative for which checks an installation actually runs and run the focused command explicitly when a target needs that report.
- `governance/handbooks/target/<language>/style-guide.md`, `governance/policies/LANG-001.json`, `governance/policies/LANGSTYLE-001.json`, and the `generated_by: pancreator-target-language-handbooks` lookup rows are generated by `/pan-build-docs`. Do not hand-edit them; regenerate the bundle when detected languages or target conventions change. They are intentionally absent from the hand-maintained `governance/policies/index.md` and `governance/handbooks/index.md`. `./bin/pan technologies detect --json` currently reports `javascript` and `typescript` with no unsupported evidence, which is the bundle this checkout carries.
- The generated bundle is split. `LANG-001` carries the toolchain instructions and MUST declare no `guidance_sources`; it binds to `coder`, `qa-tester`, `reviewer`, and `spotfixer` on `*`/`*`. `LANGSTYLE-001` carries every generated handbook as its `guidance_sources` and binds to exactly one row, `librarian`/`standalone`/`style`. That style row sits beside the unmarked `librarian`/`standalone`/`style` row for `TSTYLE-001` and `PYSTYLE-001`; the two coexist because a lookup-row identity includes its policy list.
- `validateTargetLanguageHandbooks` returns `passed` immediately when the root is not a target installation, so the bundle's coverage is not deterministically enforced in this self-development checkout even though the bundle exists here.
- `bin/install` copies `governance/` wholesale into the target staging tree, so a fresh install carries this checkout's JavaScript and TypeScript handbooks until `/pan-build-docs` regenerates them against the real target. `preserveLanguageGovernance` in `bin/install-support` keeps a complete marked split bundle across refresh and discards a malformed one for rebuild. That function is a deliberate mirror of `src/lib/validators/target-language-handbooks.ts` and must change with it.
