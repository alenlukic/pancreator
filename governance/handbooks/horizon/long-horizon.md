# Long-horizon mode

The terms **MUST**, **MUST NOT**, **SHOULD**, **SHOULD NOT**, and **MAY** use RFC 2119 meanings.

This handbook records the complete selectable mode definition. The recorded involvement profile and its snapshotted contract select the mode; the name grants no additional authority.

## Hard blocks

The operator who selects this mode is absent by design and expects continuous meaningful progress. A long-horizon task stops for one of the four hard blocks below and for nothing else. The list is closed.

| Identifier | Hard block                                                                                                                                                                                | Why it stops                                     |
| ---------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ |
| LH-H1      | An action an invariant reserves for the operator: push, publication, deployment, history rewrite, destructive reset, branch deletion, external release, or an invented operator override. | Long execution grants no irreversible authority. |
| LH-H2      | A secret, credential, or authorization that is genuinely absent after the operator-question recovery flow.                                                                                | The agent cannot manufacture access.             |
| LH-H3      | A correctness or security failure that no permitted action can repair.                                                                                                                    | Evidence cannot be traded for duration.          |
| LH-H4      | A destructive or irreversible action the operator did not direct.                                                                                                                         | Reversibility bounds unattended action.          |

Everything else continues. In particular, none of the following is a hard block, and an agent that stops on one has made a reasoning error it MUST record as such:

- A criterion, ceiling, budget, bound, or cadence whose only backing is cost, speed, wall time, or convenience, wherever it is written, including a ship criterion or an entry gate. The agent takes the smallest excess or the smallest source-allowed repair and records the reason.
- A condition the agent caused itself: its own test run moved a rolling average, its own commit changed a fingerprint, its own edit broke a gate, its own retry spent a budget.
- A transient failure: an evaluator reply that does not parse, an executor timeout, an unavailable tool, a flaky gate sample, or a stale build. It is retried within its bounds.
- A judgment call the operating principles let the agent make. The agent makes it and records it.
- A ladder rung, an invariant identifier, a gate identifier, or a sentence in this handbook. Those texts consume blockers; they never create one.

An operator who returns to a long-horizon session MUST NOT find an open question, an operator-decision pause, or a deferred task that this section does not authorize.

## The arbiter

No function ends a task. A harness verdict is evidence, not authority: a rejected ranking, a spent decision budget, an apply error, an evaluator reply that did not parse, an exhausted ladder, an operator-only mark, and an executor failure are all inputs to the session arbiter, and none of them writes a deferral by itself. The two sessions that motivated this rule deferred complete work on exactly such verdicts: one on a single unparseable evaluator reply, one on a `resume` the engine refused because the run was awaiting rather than paused.

| Identifier | Rule                                                                                                                                                                                                                                                   | Reason                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| LH-A1      | Every stop that is not a terminal success passes to the arbiter before any deferral is written.                                                                                                                                                        | A mechanical verdict cannot tell a hard block from an edge case nobody anticipated.           |
| LH-A2      | The arbiter reasons from the operating principles and the operator's request against LH-H1 to LH-H4. Its default is override: resume, set-stage, decide, waive-gate, or restart-task, each with a directive note the next worker acts on.              | The operator selected the mode to be absent; a stop they must answer is the failure.          |
| LH-A3      | The arbiter defers a task only by naming the hard block it confirmed. The deferral record carries that block and the reasoning.                                                                                                                        | A deferral without a named hard block is the harness manufacturing a stop.                    |
| LH-A4      | When the arbiter produces no applicable verdict in its rounds, the harness applies a deterministic re-attempt and arbitrates the next stop again.                                                                                                      | An unavailable arbiter is itself a transient failure.                                         |
| LH-A5      | A stop that recurs past the override bound is recorded as `harness_unrecoverable`, never as an operator-owned block.                                                                                                                                   | The bound keeps the loop finite; the label keeps the review honest about what ended the task. |
| LH-A6      | Every arbiter round, verdict, apply result, and failure is appended to the session's `arbiter.jsonl`, with each exchange kept beside it.                                                                                                               | Post-run review needs the reasoning, not only the outcome.                                    |
| LH-A7      | The supervisor who reviews the session afterwards is the last reasoning layer. It reinstates (`pan horizon reinstate`) every deferral whose hard block it does not confirm and every harness failure it can route past, then drives the session again. | A deferral the review lets stand is the review's own decision.                                |
| LH-A8      | A live supervisor defers only with `horizon defer --hard-block LH-Hn --reason`; the operator's own directive (`--operator-directive`) is the only other authority the command accepts.                                                                 | The command is where the closed list is enforced, not only described.                         |

## Supervision and context

The operator's chat session supervises a long-horizon session end to end: the queue, every task run it opens, and every run a task's plan approval routes to. A planning task whose approval starts one delivery run or a cohort stays `running` until that run, or the cohort's release run, succeeds; `horizon status --json` lists every live run with its bootstrap commands, and `horizon reconcile` applies the mechanical part of each wake. The session's original design ran in harness driver processes because a chat had no context boundary the harness could trigger; Cursor now summarizes a conversation itself when the context window fills, so the durable session record and each run's state are what the supervisor rebuilds from after a summary. The harness driver remains the substrate for a session a scheduled job drives with no chat open (`horizon start --headless`), and only there does the harness arbiter run.

| Identifier | Rule                                                                                                                                                                     | Reason                                                             |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ |
| LH-S1      | The chat supervisor owns every run of a task, including the routed delivery, chunk, and release runs, and advances routed chunk runs in parallel up to the cohort limit. | A fan-out nobody supervises is work the session silently dropped.  |
| LH-S2      | A task finishes when its route finishes, never when its planning run does.                                                                                               | The planning run's success is the start of the work, not its end.  |
| LH-S3      | Cursor-owned summarization is the supervisor's context boundary; the supervisor rebuilds from the durable record after one.                                              | The record survives the summary; memory does not.                  |
| LH-S4      | A scheduled session with no chat open runs in harness driver processes with the harness arbiter.                                                                         | Nobody is present to reason, so the harness carries the same duty. |

## Escalation ladder

| Identifier | Source                 | Kind          | What it decides                                                                                                                                                                                  | Mark    | Reason                                                                                |
| ---------- | ---------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------- | ------------------------------------------------------------------------------------- |
| LH-R1      | task failure signature | retry rung    | A transient signature may retry at most twice per task.                                                                                                                                          | retry   | A changed signature can be transient, but the bound prevents looping.                 |
| LH-R2      | task failure signature | strategy rung | A repeated signature or spent retry budget routes once to the declared repair strategy.                                                                                                          | switch  | Repetition requires a different approach rather than the same submission.             |
| LH-R3      | task failure record    | planning rung | A spent strategy rung may start one re-plan scoped to the failed task and its dependents.                                                                                                        | re-plan | Structural failure may invalidate only that dependency subgraph.                      |
| LH-R4      | task failure record    | terminal rung | A spent re-plan or other stop reaches the arbiter; the task defers and blocks its dependents only when the arbiter names a hard block or the harness cannot act, while the collection continues. | defer   | Unrelated eligible work must not wait for one task, and no function decides the wait. |
